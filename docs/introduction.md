# 验一遍 · 程序介绍

> 交付前先验一遍：把要发出去的文本贴进来，选一个模板，30 毫秒内拿到「能不能直接交」的结论和逐条可定位的修改点。
> 纯本地计算，不联网、不登录、不留历史。

---

## 1. 这个程序解决什么问题

写周报、发通知、提交项目说明、交付一段正式文字时，问题通常不是错别字，而是下面这几类：

- 该说的没说（周报没有风险段、通知没有地点）；
- 说了但不承载信息（"全面赋能""打造闭环""唯一选择"）；
- 说法站不住（"提升 40%"却没有口径，"百分之百""彻底解决"这类绝对化）；
- 形态不对（超长没人读完、一整块没有分段、感叹号当标点用）。

拼写检查器不管这些，语法检查器也不管。**验一遍**把这类"交付前的最后一公里"做成可执行的判定：内置模板给出明确阈值，输出三档结论 + 逐条缺陷（能定位的给出原文区间），让人在按下发送键之前知道该改哪一句。

它**不**做的事见 §8：不判断事实真假、不代写、不做排版。

## 2. 它做什么：7 项检查 + 1 个前置

判定完全由代码里的规则决定（见 §7 的一致性保证），同一个模板、同一段文本，任何一次运行结果逐字节相同。

| # | 检查项 | 类别 | 严重度 | 触发条件 | 能否定位原文 |
|---|---|---|---|---|---|
| 0 | 全文为空 | 格式 | high | 去掉所有空白后计数为 0；命中后**立即返回**，不再跑其余检查 | 否 |
| 1 | 长度 | 长度 | mid | 实际字数 > 模板上限 | 是（从第 maxChars 字处到末尾） |
| 2 | 要素覆盖 | 要素覆盖 | high | 模板要求的某类内容全文找不到（按正则匹配） | 否（要求自己补一段，不能用别的段落顶替） |
| 3 | 禁用项（套话） | 禁用项 | mid | 命中模板禁用词表，**逐词全量扫描**，每次出现各算一条 | 是（词的首尾区间） |
| 4 | 感叹号 | 语气 | low | 全角 ！ 与半角 ! 合计超过模板允许数 | 是（第 maxExclaim+1 个） |
| 5 | 绝对化表述 | 语气 | mid | 命中绝对化正则（"所有/一定/彻底/百分之百"一类） | 是（首处） |
| 6 | 段落 | 格式 | low | 按连续换行切段后，段数 < 模板最少段 | 否 |
| 7 | 量化断言 | 事实一致性 | mid | 出现具体数字/百分比/增幅但全文没有出处 | 是（首处） |

几条口径必须说清楚，否则容易误读结果：

- **字数口径**：按 UTF-16 码元计数（ASCII 与汉字各算 1，emoji 算 2），且**先剔除所有空白**——所以"20000 字上限"比直觉更宽松，同时与界面/CLI/内核显示的 `chars` 是同一个数。模板里的"上限 N 字"用的是**同一个口径**。
- **量化断言只提醒、不判真假**：它检测"有数字没出处"，不会也不该去核实数字是否正确。
- **要素覆盖用正则**：模板要素由关键词族匹配（例如周报的"风险"匹配 风险/问题/阻塞/卡点/隐患），可能出现"词在但意思不同"的误判，最终由人判断。
- **缺陷排序**：先按严重度（high → mid → low）稳定排序；高亮区间按位置升序，重叠的只保留靠前的那个。

## 3. 五套模板：判定规则的载体

同一段文字按不同模板判，结论可以完全不同——因为模板决定阈值与要素。

| 模板 ID | 名称 | 适用 | 字数上限 | 最少段 | 感叹号 | 必需要素 | 禁用词示例 |
|---|---|---|---|---|---|---|---|
| `weekly` | 周报 | 周期性汇报：做了什么 / 接下来做什么 / 卡在哪 | 300 | 2 | 1 | 进度、计划、风险 | 赋能、闭环、抓手、生态位、全面提升…（7） |
| `notice` | 通知公告 | 什么时候、在哪里、谁参加、要做什么 | 200 | 1 | 2 | 时间、地点、对象、要求 | 赋能、闭环、抓手（3） |
| `readme` | 项目说明 | 仓库门面：为什么做、做到什么程度、怎么跑、有什么坑 | 500 | 2 | 0 | 背景、目标、用法、限制 | 颠覆、革命性、行业领先、唯一选择…（5） |
| `general` | 通用交付 | 不确定归类时的兜底：只查长度/语气/套话/结构 | 600 | 2 | 1 | —（不查要素） | 赋能、闭环、抓手、颠覆、革命性…（7） |
| `agentcmd` | Agent 命令验收 | 交给 Agent 执行的命令：区块齐全、边界清楚、可验收 | 1200 | 5 | 0 | 角色、背景、步骤、约束与边界、验收标准 | 尽量、大概、差不多、酌情…（8，模糊词） |

> `agentcmd` 是 v1.7 新增的第 5 套模板（`RULE_VERSION` 随之升到 `yyb-3`），五个区块即五个必需要素，缺一个就是一条 `high`，标签直接写区块名（例如「缺「步骤」」）。详见 [template-agent-command.md](template-agent-command.md)。
>
> 注意：模板的"字数上限"是**判定规则**，不是输入框的软提示。超过就产生一条 `mid` 缺陷，结论因此落到"建议改一遍再交"。
> 与输入层 20,000 码元的**硬上限**是两件事：后者只决定"能不能提交校验"，前者决定"合不合格"。

## 4. 结论怎么读

| 结论 | class | 触发 | 附带的 why 文案 |
|---|---|---|---|
| 不建议直接交付 | `is-bad` | 存在 ≥1 条 high | 有 N 处需要先补内容，补完再交。 |
| 建议改一遍再交 | `is-warn` | 无 high，有 ≥1 条 mid | 没有缺项，但有 N 处说法或长度值得修。 |
| 可以交付 | `is-ok` | 无 high 也无 mid（low 不影响结论） | 这套模板的检查项都过了。事实出处仍需你自己确认。 |

结论之外还有两类信息一起返回：**缺陷列表**（类别、严重度、标签、解释、可选区间）与**通过项**（长度 78/300、要素·进度、感叹号 1/1、段落 3 这类"已经过了哪几条"）。通过项的意义是让人知道"不是没查"，而不是只看到一个红字。

## 5. 三种用法

### 5.1 命令行：`yyb-check`

与图形界面共用同一个内核绑定层，无窗口也能跑，用于 CI、装机自检、排查"是界面还是内核的问题"。

```bat
yyb-check --version                     :: 打印规则版本，如 yyb-3
yyb-check --templates                   :: 五套模板的完整阈值与词表（JSON）
yyb-check --samples                     :: 内置示例文本（JSON）
yyb-check weekly 周报.txt                :: 校验单个文件，每文件一行 JSON
yyb-check notice a.txt b.md c.docx      :: 多文件，逐行输出
yyb-check --dump x.docx                 :: 排障：只打印读入层抽出的正文
```

单文件输出形如：

```json
{"file":"...","encoding":"UTF-8","result":{"chars":78,
  "defects":[{"type":"要素覆盖","sev":"high","label":"缺「风险」","start":-1,"end":-1,"explain":"..."}],
  "passes":["长度 78/300","要素·进度","要素·计划","感叹号 1/1","段落 3"],
  "verdict":{"cls":"is-bad","text":"不建议直接交付","why":"有 1 处需要先补内容，补完再交。","high":1,"mid":2,"low":0}}}
```

### 5.2 图形界面

仓库内的 `shell/` 是一个**最小壳页**（零框架、零打包器、编译期内嵌进 exe）：模板 chip、文本框、字数与上限状态、"查一遍 / 打开文件… / 填入示例"、结论横幅、缺陷与通过项列表、Ctrl+Enter。它的存在是为了让"内核 → C ABI → Tauri 命令 → 前端"这条链路可被端到端验证。

面向日常使用的完整界面（批量校验、报告导出、AI 修改面板、明暗主题等）**不属于本仓库**，本仓库只提供它依赖的全部后端能力（见 §5.3）。

### 5.3 集成调用：13 个 Tauri 命令

前端只需 `window.__TAURI__.core.invoke`，不需要 npm 包、不需要 dev server。

| 命令 | 作用 |
|---|---|
| `api_version` | 规则版本（`yyb-3`） |
| `list_templates` / `list_samples` | 模板阈值与词表 / 内置示例 |
| `check_text(text, templateId)` | 粘贴文本校验 |
| `load_text_file(path)` | 读入单个文件（自动识别编码、支持 .docx） |
| `check_files(paths, templateId)` | 批量：逐文件读入+校验，单文件失败不中断 |
| `pick_text_files` / `save_report` | 系统文件对话框（选文件 / 保存报告） |
| `limits_info` | 硬上限（20000 码元 / 8 MB / 200 份 / 200 MB） |
| `ai_get_config` / `ai_set_config` / `ai_cancel` / `ai_revise` | 可选的 AI 修改通道（见 §8.2） |

## 6. 文本从哪来：读入层

| 输入 | 处理 |
|---|---|
| `.txt` / `.md` | 按 BOM 与内容猜编码：UTF-16LE/BE BOM → 严格 UTF-8 → GB18030（覆盖国内常见中文文件）；解码是**宽容**的，坏字节变 U+FFFD 而不是报错 |
| `.docx` | 解压读 `word/document.xml`，只取正文文本：段落 → 换行，表格按文档顺序拍平成段落，`tab`→空格、`br`→换行；超链接文字保留 |
| `.pdf` | **暂不支持**，明确返回错误码（选型已定 lopdf，尚未实施） |
| `.doc` | **暂不支持**（Word 97-2003 二进制格式） |
| 其它/二进制 | 先判"像不像文本"（含 NUL 或大量控制符即拒绝），避免把随机二进制当正文 |

硬上限（`limits.rs`，一个真源、五处生效）：单份 20,000 码元、单文件 8 MB、批量 200 份 / 200 MB、docx 解压后 XML 64 MB。超出返回 `E_TOO_LARGE`，文案与阈值同源。

错误码是可读的：`E_TOO_LARGE`、`E_NOT_TEXT`、`E_UNSUPPORTED_FORMAT`、`E_IO`、`E_DOCX_MALFORMED`、`E_DOCX_NO_TEXT`、`E_TEMPLATE`、`E_JSON`，AI 通道另有 `E_AI_*` 系列。

## 7. 技术形态与一致性保证

~~~
┌────────────── 前端（shell/ 或独立界面） ──────────────┐
│  window.__TAURI__.core.invoke(command, args)          │
└──────────────────────┬───────────────────────────────┘
                       │ Tauri IPC（进程内，JSON）
┌──────────────────────▼───────────────────────────────┐
│ Rust 层：commands.rs（整形/批量/上限）                 │
│          text_io.rs + docx.rs（字节 → 文本）           │
│          core_ffi.rs（extern "C" 绑定）               │
└──────────────────────┬───────────────────────────────┘
                       │ C ABI（同进程，UTF-8 + 显式长度）
┌──────────────────────▼───────────────────────────────┐
│ C++17 内核 core/：规则、模板、正则引擎（MiniRE）        │
│ 无 IO、无全局状态、纯函数：文本 + 模板 → 结果           │
└──────────────────────────────────────────────────────┘
~~~

为什么这样分层：

- **内核用 C++ 且无 IO**：单文件纯计算，可被 CLI、GUI、未来的移动端壳共用；判定逻辑只有一处，避免两端实现漂移。
- **Rust 层只做 IO 与整形**：解码、docx 解包、上限、批量、对话框、报告落盘；不参与判定。
- **同进程调用而非 sidecar**：无额外进程、无端口、无额外防火墙/杀软摩擦，启动即可用。

**一致性是门禁，不是承诺**：仓库里同时存放规格副本（`tools/parity/spec/yanyibian.js`，Web 端原始实现）与 C++ 实现，`tools/parity` 用固定种子生成 **538 条语料**（五模板示例、8 种空白形态、长度边界、要素正则扫描、禁用词/感叹号/段落/量化短语、代理对/BOM/零宽/U+2028、220 条随机文本），逐键 deep-equal 比对，要求 **100% 全绿**；规则改动必须同时改两处并递增 `RULE_VERSION`（当前 `yyb-3`）。**回归一旦不一致，构建门禁直接失败。**

## 8. 明确的边界

### 8.1 不做

- 不判断事实真假，不核实数字来源，不联网查证；
- 不代写、不改写正文（AI 通道是可选能力，见 8.2，且默认关闭）；
- 不做排版与格式转换（Markdown/Word 样式不在范围内）；
- 不留历史、不做账号、不做云同步、不做埋点；正文不落盘——默认只在内存里过一遍。
- 不保证"可以交付"等于"内容正确"：结论只覆盖本程序能机械检查的部分。

### 8.2 可选的 AI 修改通道（默认关闭）

判定之外，另有一条**用户自带 API Key** 的通道：把缺陷清单与正文发给用户指定的 OpenAI 兼容服务，取回"逐处修改建议"，本地按守卫落地并**重新校验**，产出三件套（修改稿 / 变更说明 / 复检结果）。

约束是硬性的：默认关闭、关闭时零外联；开启需显式保存配置；数字/百分比/日期/金额默认**不允许**改（需显式放开）；改动必须能在原文唯一匹配，否则整条拒收；改后超上限则倒序丢弃；AI 结果**不计入结论**（`type=语义建议, sev=low`），保证规则判定与 Web 端逐键一致。

已知限制：密钥在本机持久化（明文存于 WebView 的 localStorage，加密方案尚待补充）；该通道的界面不属于本仓库，命令仍注册可用。

## 9. 一次完整的使用（真实输出）

输入（周报模板）：

~~~text
本周完成了数据采集脚本的重构，采集速度提升 40%，整体流程更加顺畅。
下周计划把三条试点记录补齐，并同步更新标注规范。
整个方案全面赋能后续实验，效率显著提升！
~~~

结论：**不建议直接交付** —— 有 1 处需要先补内容，补完再交。

| 严重度 | 缺陷 | 类别 | 位置 | 为什么 |
|---|---|---|---|---|
| high | 缺「风险」 | 要素覆盖 | 无 | 全文没有"风险/问题/阻塞/卡点"一类内容，而周报的读者最需要知道这块 |
| mid | 套话「赋能」 | 禁用项 | 67–69 | 换成具体做了什么、得到什么结果 |
| mid | 量化断言 2 处 | 事实一致性 | 19–23 | 出现具体数字（如"提升 4"）但没有出处，补一句口径 |

通过项：长度 78/300、要素·进度、要素·计划、感叹号 1/1、段落 3。

（"提升 4"来自正则把"提升 40%"切成"提升 4" + "40%"两处命中——这是既定规则，不是 bug；见 docs/parity.md。）

## 10. 已知限制

| 项 | 现状 |
|---|---|
| 判定范围 | 只覆盖机械可查项（长度/要素/套话/语气/结构/量化提醒），语义与事实不查 |
| 要素匹配 | 关键词正则，存在"词在而意思不同"的误判，需人判断 |
| 量化断言 | 只提醒"有数字无出处"，不判数字对错 |
| PDF / .doc | 不支持，返回明确错误码 |
| docx | 只取正文文本，不保留表格结构、样式、批注、页眉页脚 |
| 编码 | 解码宽容（坏字节 → U+FFFD），极端损坏文件可能得到看似正常但残缺的文本 |
| 平台 | Windows 10 1809+ / 11 x64（NSIS 安装包，装到用户目录，免管理员）；移动端待定 |
| AI 通道 | 默认关闭；密钥明文持久化（加密待补充）；界面不在本仓库 |
