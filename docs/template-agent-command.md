# Agent 命令验收模板（`agentcmd`）

> 验收对象：**一段交给 Agent 执行的命令**（任务书 / prompt / 执行工单）。
> 判定方式：与其余模板相同——**阈值即规则**，由 C++ 内核机械判定，输出三档结论并可定位到具体区块。

## 0. 定位、命名、适用场景

| 项 | 内容 |
|---|---|
| 模板 ID | `agentcmd` |
| 显示名 | Agent 命令验收 |
| 副标题（界面副文案） | 角色 / 背景 / 步骤 / 约束 / 验收 |
| 适用场景 | 把任务交给 Agent 之前，先自检这份命令是否"能被执行、能被验收"：交接给同事的 AI 任务书、CI 里的自动化执行单、外包/协作方的操作指令 |
| 不适用场景 | 面向人的通知公告（用 `notice`）、周期汇报（用 `weekly`）、项目门面（用 `readme`）、不确定归类（用 `general`） |
| 判定参数 | 上限 20000 字 · 最少 5 段 · 感叹号 0 个 · 5 个必需要素 · 8 个模糊词 |

**与现有 4 套模板的关系**：并列的**第 5 套**，机制完全一致（模板 = 阈值 + 必需要素 + 禁用词 + 段落/感叹号约束），不引入新的检查类型，因此不改变既有 4 套的任何判定结果。它与它们的差异只在"判什么要素"：周报判进度/计划/风险，通知判时间/地点/对象/要求，项目说明判背景/目标/用法/限制，而命令验收判**角色/背景/步骤/约束与边界/验收标准**。

> **(待补充：是新增还是替换)** —— 本模板按「**新增第 5 套**」实施（现有 4 套原样保留、判定行为零改动）。若你的本意是"用它替换某一套"，请指明替换哪一套，我再调整（替换会改变既有模板集合，属破坏性变更）。
> **(待补充：是否升级 RULE_VERSION)** —— 本模板按「**升级到 `yyb-3`**」实施（新增模板改变了判定规则集合，门禁要求两端同改并递增版本）。若希望版本号保持 `yyb-2`，需你确认——那会让"规则版本"不再能唯一标识判定行为。
> **v1.8 调整**：按第四轮要求，长度上限由 1200 改为 **20000 字**（与输入硬上限一致，长度项实际不触发），段落 5 / 感叹号 0 / 5 要素不变，`RULE_VERSION` 升到 **`yyb-4`**；每套模板示例补到 3 条（共 15 条）。禁用词清单仍在（待补充）状态，本轮未改，见 §11。

## 1. 角色（区块一）

**必填项**

- `## 角色` 区块标题（缺标题也可，正文出现"角色/身份/你是/作为/担任"任一即可通过机械判定，但标题让结论可定位到区块）
- 执行者身份（谁来做）
- 职责范围（负责什么）
- **不负责什么**（最容易漏、也最容易引发越界）
- 交付对象（结果给谁看）

**模板骨架**

~~~text
## 角色
- 你是【待填：执行者身份，如「发布工程师」】。
- 负责：【待填：2–3 条职责】。
- 不负责：【待填：明确排除的事，如「不改业务代码」】。
- 结果交付给：【待填：人/系统/文档位置】。
~~~

## 2. 背景（区块二）

**必填项**

- 现状（现在是什么状态）
- 触发原因（为什么要做这件事）
- 已知前提（版本号、环境、依赖的系统）
- 与本次任务相关的历史事故/返工（有则填）

**模板骨架**

~~~text
## 背景
- 现状：【待填：当前版本/环境/数据状态】。
- 原因：【待填：为什么要做，触发事件是什么】。
- 前提：【待填：依赖的系统、账号、数据、版本】。
- 相关历史：【待填：上次失败/回滚的原因，没有则写「无」】。
~~~

## 3. 步骤（区块三）

**必填项**

- 3–7 条编号步骤（少于 3 条通常说明拆得不够）
- 每条含：**动作 + 输入 + 输出 + 失败怎么办**
- 步骤之间不允许出现"然后看着办"这类空档

**模板骨架**

~~~text
## 步骤
第1步：【待填：动作】。输入：【待填】。输出：【待填】。失败时：【待填：停止/重试/上报】。
第2步：【待填：动作】。输入：【待填】。输出：【待填】。失败时：【待填】。
第3步：【待填：动作】。输入：【待填】。输出：【待填】。失败时：【待填】。
~~~

## 4. 约束与边界（区块四）

**必填项**

- 禁止项（不能碰的数据/环境/命令）
- 允许范围（可改的目录、可用的命令白名单）
- 资源上限（时间、次数、体积、并发）
- 人工确认点（什么情况下停下来问人）

**模板骨架**

~~~text
## 约束与边界
- 禁止：【待填：如「禁止直连生产库」】。
- 允许范围：【待填：可改目录/可用命令白名单】。
- 上限：【待填：单次超时、重试次数、体积上限】。
- 停下来问人：【待填：不确定/超限/需要删除时】。
~~~

## 5. 验收标准（区块五）

**必填项**

- 可执行的判据（命令 + 期望输出，或可核对的事实）
- 「全部通过才算完成」的清单
- 允许的例外（如"允许 1 条已知告警"）
- 不通过时的处置（回滚 / 重做 / 上报）

**模板骨架**

~~~text
## 验收标准
- 【待填：命令】执行后输出【待填：期望值】。
- 【待填：检查项】无异常（允许的例外：【待填】）。
- 任一项不满足：【待填：回滚/重做/上报给谁】。
~~~

## 6. 判定映射：区块如何变成结论

模板的五个区块就是五个**必需要素**；每个缺失都会产生一条 `high` 缺陷，标签直接写区块名，因此结论天然可定位到区块。

| 区块 | 引擎检查项 | 命中判据（正则） | 缺失时输出 | 严重度 | 对结论的影响 | 能否定位原文 |
|---|---|---|---|---|---|---|
| 角色 | 要素覆盖 | `角色|身份|你是|作为|担任` | 缺「角色」 | high | 不建议直接交付 | 否（要求自己补一段） |
| 背景 | 要素覆盖 | `背景|上下文|现状|起因|为什么|目前` | 缺「背景」 | high | 不建议直接交付 | 否 |
| 步骤 | 要素覆盖 | `步骤|流程|第[一二三四五六七八九十0-9]步|依次|逐个` | 缺「步骤」 | high | 不建议直接交付 | 否 |
| 约束与边界 | 要素覆盖 | `约束|边界|禁止|不得|不要|只允许|上限|范围|白名单|黑名单` | 缺「约束与边界」 | high | 不建议直接交付 | 否 |
| 验收标准 | 要素覆盖 | `验收|通过标准|判定标准|完成标准|自检|必须满足|检查项` | 缺「验收标准」 | high | 不建议直接交付 | 否 |
| 模糊措辞 | 禁用项 | 词表逐处扫描（8 词） | 套话「尽量」… | mid | 建议改一遍再交 | **是**（词的首尾区间） |
| 结构 | 段落 | 段数 < 5 | 只有 N 段 | low | 不影响结论 | 否 |
| 长度 | 长度 | 字数 > 1200 | 超出 N 字 | mid | 建议改一遍再交 | **是**（第 1201 字起） |
| 语气 | 感叹号 | ！+! > 0 | 感叹号 N 个 | low | 不影响结论 | **是**（第 1 个） |
| 语气 | 绝对化表述 | 内核全局词表（所有/一定/彻底/百分之百…） | 绝对化表述 N 处 | mid | 建议改一遍再交 | **是**（首处） |
| 事实一致性 | 量化断言 | 数字/百分比/增幅但无出处 | 量化断言 N 处 | mid | 建议改一遍再交 | **是**（首处） |

三档结论的判定口径与其余模板完全相同（`core/src/yyb_engine.cpp` 的 `verdict_of`，单一实现）：

| 结论 | 触发条件 |
|---|---|
| 不建议直接交付（`is-bad`） | 存在 ≥1 条 high（即至少缺一个区块） |
| 建议改一遍再交（`is-warn`） | 无 high，存在 ≥1 条 mid（模糊词 / 超长 / 绝对化 / 量化断言） |
| 可以交付（`is-ok`） | 无 high 无 mid（low 不影响） |

## 7. 两份完整范例

### 7.1 合规范例（可直接抄，预期结论：可以交付）

~~~text
角色：你是发布工程师，负责把 0.2.0 发到测试环境；不负责改业务代码。
背景：上一版发布漏了迁移脚本，回滚过一次；现在测试环境停在上一版。
步骤：第1步跑全量测试并保存日志；第2步构建产物并核对版本号；第3步部署到测试环境；第4步回填发布记录。
约束与边界：禁止直连生产库；改动范围只允许在 build 目录内；单次部署超时上限 10 分钟，超时先停手并上报；遇到不确定项先停下来问。
验收标准：测试全部通过；部署后健康检查接口返回 200；日志里没有 ERROR 级别的记录；以上任一项不满足就回滚。
~~~

### 7.2 不合规范例（内置示例，预期结论：不建议直接交付）

~~~text
角色：你是发布工程师，负责把 0.2.0 发到测试环境。
背景：上一版发布漏了迁移脚本，回滚过一次。
步骤：第一步先跑全量测试，第二步构建产物，第三步部署并按步骤尽量核对结果。
验收标准：测试全绿、部署后接口返回 200。
~~~

预期缺陷（3 条）：

| 严重度 | 缺陷 | 区块 | 原因 |
|---|---|---|---|
| high | 缺「约束与边界」 | 区块四 | 没有禁止项、范围、上限、人工确认点 |
| mid | 套话「尽量」 | 区块三 | "尽量核对"把判断权交回给 Agent |
| low | 只有 4 段 | 全文 | 少于最少 5 段 |

## 8. 怎么用

~~~bat
:: 命令行
yyb-check agentcmd 任务书.txt
:: 图形界面：第 5 张模板卡「Agent 命令验收」，粘贴后 Ctrl+Enter
~~~

## 9. 已知限制与待补充

| 项 | 现状 / (待补充) |
|---|---|
| 要素判定深度 | 只判"区块在不在"，不判角色写得准不准、步骤是否可执行 |
| 禁用项标签 | 引擎统一输出「套话「X」」；本模板的禁用词其实是**模糊词**。**(待补充：是否把标签改成「禁用词「X」」——该文案改动会同时影响现有 4 套模板的输出，属规则版本变更)** |
| 字数上限 1200 / 最少 5 段 | 依据"五区块各一段 + 每段 200 字左右"估的。**(待补充：是否调整；调整需同改两端并重算语料)** |
| 模板 ID | 采用 `agentcmd`。**(待补充：命名是否采用；改名需同步语料与文档)** |
| 命令可执行性 | 不检查命令语法、不联网、不试跑——纯文本判定 |
| 与 AI 通道的关系 | AI 修改通道不了解"区块"概念，它按缺陷列表给建议；对缺区块的 high 缺陷通常只能提示补写，不会代写 |

## 11. v1.8 本轮调整（第四轮）

| 项 | 本轮取值 | 说明 |
|---|---|---|
| 模板集合 | 5 套不变 | 既有 4 套参数与文案零改动，判定结果与改动前逐键一致（parity 593/593） |
| 长度上限 | `agentcmd` **20000 字** | 与输入硬上限 `MAX_UNITS = 20000` 一致；超 20000 的正文在输入层就被拒，因此本模板的「长度」检查实际不会触发。段落 5 / 感叹号 0 保持原值（未指定即不改） |
| 示例数量 | 每套 3 条，共 15 条 | `SAMPLE_SRC` / `SAMPLES` 同一份文案；壳页「随机示例」按当前模板抽取，连续两次不重复，并显示示例标题 |
| 禁用词 | 仍为 8 个模糊词 | **未改**：新的清单属（待补充），候选见下；改动需两端同改 + 语料重算 |
| AI 接口 | 壳页恢复入口 | `ai_get_config` / `ai_set_config` / `ai_cancel` / `ai_revise` 四个命令本轮前就存在，本轮补回壳页表单与「生成修改稿 / 取消 / 应用到编辑器 / 复制交付包」；Key 只存内存 |

**禁用词候选（待确认清单与数量，本轮不实施）**：

1. 保留现状：尽量 / 大概 / 差不多 / 酌情 / 适当 / 看情况 / 有时间 / 应该没问题（8 个，模糊词）。
2. 扩到「含糊数量」：上述 8 个 + 若干 / 数个 / 一些 / 左右 / 上下。
3. 扩到「推卸式措辞」：上述 8 个 + 你看着办 / 自行判断 / 灵活处理 / 视情况。
4. 改为混入通用套话：上述 8 个 + 赋能 / 闭环 / 抓手。

> 注意：引擎的禁用项标签统一写作「套话「X」」（`core/src/yyb_engine.cpp`），而本模板禁用词是模糊词；若要把标签改成「模糊词「X」」需改内核文案并重算金标准（属规则变更，要再升一次 `RULE_VERSION`）。此点 v1.7 已提出，仍未裁定。
